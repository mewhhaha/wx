# Web large-document soak

The scheduled Chromium soak is intentionally separate from unit tests, the PR smoke project, and the cross-browser DOM matrix. It runs a deterministic 20,000-line workload for ten minutes by default and writes `soak-summary.json`, a trace, video, screenshot, and replay metadata. If browser evaluation, language convergence, or a later assertion fails, `soak-failure.json` is always written and attached with the seed, requested duration, phase, action index/count, completed count, PRNG state, recent 200 fully specified actions, and error stack. The browser continuously mirrors that checkpoint to `window.__wxSoakCheckpoint` and the Playwright process, so a page crash or navigation still leaves the last reported checkpoint.

```sh
pnpm test:e2e:soak

# Fast local replay of a CI failure
WX_SOAK_SEED=1592639710 WX_SOAK_SECONDS=10 pnpm test:e2e:soak
```

Replay semantics are exact: `WX_SOAK_SECONDS` produces `max(1, floor(seconds * 1000 / 12))` sustained actions. The seeded xorshift generator consumes exactly two values per action while constructing the entire schedule before execution. Each record includes every variable payload, including inserted characters and split orientation. Actions run in index order against a 12 ms target cadence; a fast browser waits for its next target, while a slow browser completes the same schedule and may overrun. Thus the default 50,000-action schedule occupies at least ten minutes, and the same seed plus seconds always executes the same complete sequence rather than a machine-dependent time-bound prefix. The live in-page checkpoint is updated for every action without cloning the action ring. Cross-process reports are coalesced and copied only every 25 completed sustained actions (plus phase boundaries and completion), keeping crash evidence current without turning the workload into an IPC benchmark.

The versioned limits live in `benchmarks/budgets/web-soak-v1.json`. The test samples key-to-paint p50/p95, long tasks, precise Chromium heap when available, DOM nodes, materialized visual rows, active workers, ResizeObserver/MutationObserver/IntersectionObserver instances, animation frames, registered listeners, and outbound worker-message bytes. It includes a no-language phase, long wrapped lines, a Tree-sitter phase, dense diagnostics, many selections, mixed movement/edit/history/search/hover/save/split actions, resize-during-use, controller-owned language-service recreation, and repeated direct-editor plus custom-element connect/disconnect cycles.

The 1,000-input pressure gate temporarily installs a test-local Blob Web Worker highlighter. Its `update` and `updateBatches` paths serialize the actual incremental `{from,to,insert}` edits; the batched path splits those edits across two bounded requests with deliberately inverted delays. The adapter validates request/reply revisions, advances only a monotonic acknowledged revision, counts an older out-of-order reply as dropped stale work, and requires the acknowledged revision to converge with both the last sent and last content-changing editor revisions (the subsequent `Escape` changes mode/selection state only). It also asserts request state is removed on reply, edit-payload bytes stay between versioned minimum and maximum limits, the view-owned worker terminates, and controller work converges. This is protocol/backpressure evidence for the test adapter, not a claim that the Blob worker runs the Tree-sitter parser. The separate in-process completion provider remains a completion workload and is not treated as worker evidence.

Resource limits are evaluated as deltas from the instrumented page baseline so Vite development-client resources do not look like editor leaks. Before that baseline is captured, the listener wrapper self-tests normal `AbortSignal` cancellation, an already-aborted signal, and `once` delivery. Every supported observer class is tracked independently with observe/unobserve/disconnect accounting, and support flags explicitly identify an unavailable browser API. The summary includes post-destroy samples every five lifecycle cycles, so worker/listener/observer/RAF growth fails at the first observed cycle rather than being hidden by one final delta. Direct-editor destruction and custom-element disconnection are checked synchronously for residual editor roots in their former light or shadow DOM.

The dedicated Chromium launch exposes V8's explicit GC. Heap growth is sampled after the same four-pass forced-GC sequence on both sides of the sustained workload while the editor is still live. Long-task observation starts after the first collection and stops before the second, so harness GC is excluded; scheduled Chromium must expose the `longtask` entry type and registration fails closed. The harness separately creates and destroys each lifecycle target in its own browser task and retains only WeakRefs to direct-editor roots and custom-element ShadowRoots. After the workload's remote-evaluation job ends, it runs up to three independent rounds of eight standalone GC jobs. Each round's dereference job ends before another round begins, avoiding both WeakRef construction and dereference keep-alives while giving Blink's detached wrapper graph bounded time to converge. The final read reports retained targets for each five-cycle cohort and for the full set; anything still retained after the bounded convergence loop fails. This is collectability evidence under that Chromium/V8 configuration; it does not prove when production browsers choose to collect, nor does it replace the synchronous residual-root check.

Cursor-only movement uses 25 warmup inputs and 120 controller-to-paint samples at the same fixed viewport for both 1,000 and 20,000 lines. Both the materialized-row shape and p95 latency are recorded. The larger document must remain within the absolute p95 budget plus explicit versioned ratio and delta limits, avoiding a timing-only or single-document claim.

The focus/blur entries are explicitly lifecycle signals within the same page; they are not claimed as a real browser-background test. Existing cross-browser DOM coverage remains responsible for real-page/background behavior. Heap measurement is optional because the browser API is not universal; all structural queue, DOM, row, and lifecycle limits remain mandatory. Chromium is the scheduled gate. The harness and seed are reusable with the DOM matrix configs for targeted Firefox/WebKit investigation, but those engines do not expose identical memory telemetry.

Rerun this tier after changes to text storage, viewport invalidation, language scheduling/protocols, DOM lifecycle, or worker ownership. Do not add it to the quick `test:e2e` command.
